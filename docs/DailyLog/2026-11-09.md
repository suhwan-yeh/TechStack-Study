## 2. CI/CD와 배포 구조 이해

### CI — 지속적 통합

코드 변경 시 빌드와 테스트를 자동으로 실행하여 정상적으로 통합되는지 확인하는 과정이다.

프로젝트에 `.github/workflows/ci.yml`을 작성하고 Push한 상태이며, 실제 실행 결과 확인은 별도로 필요하다.

### CD — 지속적 배포·전달

빌드한 결과물을 서버에 전달하고 실행하는 과정을 자동화하는 것이다.

프로젝트에서 준비 중인 배포 흐름은 다음과 같다.

```text
코드 Push
  ↓
GitHub Actions에서 빌드·테스트
  ↓
JAR 파일 생성
  ↓
S3에 배포 파일 업로드
  ↓
EC2에서 다운로드
  ↓
Java 애플리케이션 실행
  ↓
MySQL과 연결
```

오늘은 이 흐름 중 AWS 자원을 준비하고 EC2에 원격 접속하는 단계까지 진행했다.

## 3. AWS 서비스 역할 정리

| 서비스 | 역할 | 이번 프로젝트에서의 용도 |
|---|---|---|
| EC2 | 가상 서버 제공 | Spring Boot 애플리케이션 실행 |
| S3 | 파일 저장 | 배포용 JAR 및 이미지 보관 |
| IAM | AWS 접근 권한 관리 | EC2와 GitHub Actions의 S3 접근 제어 |
| 탄력적 IP | 고정 공인 IPv4 주소 제공 | EC2 접속 주소 유지 |
| 보안 그룹 | 인스턴스의 네트워크 접근 제어 | SSH 및 애플리케이션 포트 설정 |

DB는 현재 가이드에 따라 EC2 내부에 MySQL을 설치하는 방향으로 준비한다.

## 4. S3 버킷 생성

배포 파일과 이미지를 보관할 S3 버킷을 생성했다.

저장 경로는 다음과 같이 구분할 예정이다.

```text
S3 버킷
├── deploy/  → 배포용 JAR
└── images/  → 서비스 이미지
```

S3는 파일을 보관하는 역할을 하고, 애플리케이션은 EC2에서 실행한다.

---

## 5. IAM 역할과 사용자 정책 구성

### EC2용 IAM 역할

EC2에서 S3의 배포 파일을 읽고, 서비스 이미지를 관리하는 데 필요한 권한을 구성했다.

### GitHub Actions용 IAM 사용자 정책

GitHub Actions가 S3의 배포 경로에 JAR 파일을 업로드할 수 있도록 정책을 구성했다.

| 대상 | 필요한 작업 |
|---|---|
| EC2 | 배포 파일 다운로드, 이미지 읽기·업로드·삭제 |
| GitHub Actions | 배포용 JAR 업로드 |

IAM 역할과 사용자 정책을 구성했으며, 액세스 키 발급 및 GitHub Secrets 등록 완료 여부는 추가 확인이 필요하다.

## 6. EC2 인스턴스 생성

애플리케이션을 실행할 EC2 인스턴스를 생성했다.

| 항목 | 구성 |
|---|---|
| 운영체제 | Ubuntu Server 24.04 LTS |
| 인스턴스 유형 | t3.micro |
| 스토리지 | 20GiB, gp3 |
| 접속 방식 | `.pem` 개인키를 이용한 SSH |
| AWS 접근 권한 | EC2용 IAM 역할 연결 |

EC2 생성은 애플리케이션을 실행할 컴퓨터를 준비한 단계이다. 실제 앱 실행에는 Java 설치와 배포 작업이 추가로 필요하다.

## 7. 보안 그룹과 탄력적 IP 설정

### 보안 그룹

| 포트 | 설정 내용 | 목적 |
|---|---|---|
| 22 | 접속 허용 | SSH 원격 접속 |
| 8082 | 접속 허용 | 이후 애플리케이션 접근 |
| 3306 | 외부 허용 규칙 추가하지 않음 | MySQL 외부 직접 접속 제한 |

포트를 허용하는 것과 해당 프로그램이 실행되는 것은 별개이다. 8082 포트를 열었더라도 앱을 실행하기 전에는 웹서비스에 접속할 수 없다.

### 탄력적 IP

탄력적 IP를 할당하고 EC2에 연결했다.

- **할당:** AWS 계정에 고정 IP 확보
- **연결:** 확보한 IP를 EC2에 연결
- **목적:** 인스턴스 중지·시작 이후에도 같은 주소로 접속

## 8. SSH 접속 문제와 해결

### 문제 1. 개인키 파일을 찾지 못함

CloudShell에서 로컬 PC의 `.pem` 파일 경로를 사용하여 접속을 시도했다.

**원인**

CloudShell은 AWS에서 실행되는 환경이므로 내 PC의 파일 경로에 직접 접근할 수 없다.

**해결**

개인키가 저장된 로컬 PC의 PowerShell에서 실제 파일 경로를 지정하여 접속했다.

### 문제 2. 개인키 권한 오류

접속 과정에서 `UNPROTECTED PRIVATE KEY FILE` 오류가 발생했다.

**원인**

개인키 파일에 다른 사용자 그룹도 접근할 수 있도록 권한이 설정되어 있어 SSH가 키 사용을 거부했다.

**해결**

Windows의 `icacls`를 이용해 개인키 파일의 상속 권한과 불필요한 그룹 권한을 제거하고 접근 범위를 제한했다.

### 최종 결과

로컬 PowerShell에서 EC2의 `ubuntu` 계정으로 SSH 로그인하는 데 성공했다.

```text
로컬 PC의 PowerShell
  ↓
EC2의 탄력적 IP로 SSH 접속
  ↓
개인키 인증
  ↓
Ubuntu 로그인 성공
```

## 10. 새롭게 알게 된 점

1. **CI와 CD는 검증 대상이 다르다.**  
   CI는 코드의 빌드·테스트를 확인하고, CD는 서버로 전달하여 실행하는 과정을 다룬다.

2. **명령을 실행하는 위치를 구분해야 한다.**  
   로컬 PowerShell, CloudShell, SSH로 접속한 EC2는 서로 다른 실행 환경이다.

3. **개인키는 파일 내용뿐 아니라 접근 권한도 중요하다.**  
   다른 사용자에게 접근 권한이 열려 있으면 SSH 인증이 거부될 수 있다.

4. **서버 접속 성공과 웹서비스 배포 성공은 별도로 확인해야 한다.**  
   SSH 접속 이후에도 실행 환경 설치, 앱 배포, DB 연결 검증이 필요하다.

5. **SSH 접속 종료가 EC2 중지를 의미하지 않는다.**  
   `exit`는 원격 접속을 종료하며, EC2 실행 상태는 AWS 콘솔에서 별도로 관리한다.
