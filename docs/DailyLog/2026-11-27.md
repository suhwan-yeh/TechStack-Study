## 1. 웹 요청과 DB의 기본

- **HTTP 요청과 응답** — 브라우저가 서버에 처리를 요청하고 서버가 결과를 돌려준다. 여행지 목록 조회에는 보통 `GET`, 새 예약 생성에는 `POST`를 사용한다.
- **MVC** — 데이터와 업무 규칙(Model), 화면(View), 요청 처리 흐름(Controller)의 역할을 나누는 방식이다. 놀러가자에서는 Servlet이 요청을 받고 JSP가 화면에 표시할 HTML을 만든다.
- **JDBC와 JPA** — JDBC는 자바에서 DB에 SQL을 보내고 결과를 받는 API다. JPA는 자바 객체를 DB 테이블과 매핑해 저장하고 조회할 수 있게 해주는 표준이다. 놀러가자에서는 JDBC를, CRM에서는 JPA를 사용했다.

## 2. 놀러가자 · 예약과 결제

### 같은 가이드에 두 명이 동시에 예약하면?

두 요청이 저장 전에 동시에 조회하면 둘 다 “예약 가능한 날짜”라고 판단할 수 있다. 요청이 겹치면서 발생하는 **동시성 문제**다.

- **생성 컬럼** — 다른 컬럼을 바탕으로 DB가 값을 계산하는 컬럼이다.
- **`UNIQUE`** — 중복된 값을 저장하지 못하게 하는 DB 규칙이다.
- 프로젝트에서는 생성 컬럼과 `UNIQUE`를 조합해 같은 가이드·같은 날짜의 중복 저장을 막았다. 기존 예약과 충돌한 요청에는 `409 Conflict`를 반환했다.

> 면접 답변 — “조회 시점에는 두 요청 모두 빈 날짜를 볼 수 있습니다. 그래서 저장할 때도 MySQL이 중복 여부를 검사하도록 제약을 걸었습니다.”

### 결제 금액은 왜 서버에서 계산했을까?

브라우저에서 전달되는 금액은 검증이 필요한 입력값이다. 1인 요금이 3만 원이고 2명이 예약했다면 서버에서 6만 원을 계산하고, 승인 전에 결제 요청의 금액과 비교한다.

토스 결제는 **요청 → 인증 → 승인** 순서로 진행된다. `orderId`는 서비스에서 만든 주문번호이고, `paymentKey`는 토스가 발급한 결제 식별자다.

### 같은 결제 승인 요청이 두 번 들어오면?

`PENDING → CONFIRMING → PAID` 순서로 결제 상태를 관리했다. 현재 상태가 `PENDING`일 때만 `CONFIRMING`으로 바꾸는 게 **조건부 `UPDATE`**다.

```sql
-- 개념을 설명하기 위한 예시 SQL
UPDATE payments
SET status = 'CONFIRMING'
WHERE order_id = ? AND status = 'PENDING';
```

상태를 변경한 요청만 승인 API를 호출한다. 변경된 행이 0개라면 현재 주문 상태를 확인한다. 승인 성공을 확인한 뒤 `PAID`로 변경한다.

### 여행지 조회와 채팅에 쓴 기술

- **캐시와 LRU** — 이전 TourAPI 조회 결과를 재사용해 외부 호출을 줄였다. LRU는 캐시가 꽉 찼을 때 마지막 사용 시점이 가장 오래된 항목부터 제거하는 규칙이다.
- **WebSocket과 번역 API** — WebSocket은 연결을 유지하면서 서버와 브라우저가 양쪽에서 메시지를 보낼 수 있게 한다. 번역 API는 메시지의 언어를 바꾸는 역할을 한다.

## 3. 고객관리 CRM · 테스트와 자동 배포

```text
PR → JUnit 테스트 → 필수 검사 통과 → main 머지 → JAR 빌드 → EC2 배포
```

- **CI** — 코드 변경이 들어오면 자동으로 검사한다. CRM에서는 GitHub Actions가 테스트를 실행하고, 브랜치 보호 규칙이 필수 검사에 실패한 PR의 머지를 막았다.
- **CD** — CRM에서는 `main`에 합쳐진 코드를 JAR로 빌드하고 EC2에 자동 배포했다. JAR는 자바 실행에 필요한 코드와 리소스를 묶은 파일이다.
- **EC2 · S3 · IAM** — EC2는 앱을 실행하는 가상 서버, S3는 파일 같은 객체를 보관하는 저장소, IAM은 AWS 리소스에 대한 접근 권한을 관리하는 체계다. CRM에서는 EC2의 Ubuntu 환경에 MySQL 8도 설치했다.
- **단위 테스트와 통합 테스트** — 금액 계산 메서드가 `30,000 × 2 = 60,000`을 반환하는지 확인하는 건 단위 테스트다. 실제 MySQL에 중복 예약을 넣었을 때 DB 제약이 작동하는지 확인하는 건 통합 테스트다.

## 4. 고객관리 CRM · 502 장애 대응

**502 Bad Gateway**는 앞단 프록시가 뒤쪽 애플리케이션에서 유효한 응답을 받지 못했을 때 표시하는 상태 코드다. **DB 스키마**는 테이블과 컬럼 같은 DB의 구조다.

1. 서비스 재시작 뒤 공개 주소에서 502가 발생했다.
2. 서버 로그를 확인해 배포 코드가 기대하는 테이블이 운영 DB에 빠져 있음을 파악했다.
3. 팀원이 수정한 코드를 반영해 재배포했다.
4. 공개 주소에서 구글 로그인이 동작하는 것까지 확인했다.

> 면접 답변 — “서버 로그에서 배포 코드와 운영 DB의 테이블 구조가 맞지 않는 것을 확인했습니다. 팀원의 수정 코드를 반영해 재배포한 뒤 공개 주소에서 구글 로그인까지 확인했습니다.”
