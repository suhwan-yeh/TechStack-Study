# 2026-11-25 | StoreCRM 운영 배포 트러블슈팅

오늘은 AWS EC2에 배포한 StoreCRM에 도메인과 HTTPS를 적용했다. 그 과정에서 EC2 SSH 접속 실패, Google 로그인 오류, 서비스 재시작 후 502 오류를 확인하고 해결했다.

## 1. 공개 IP로 접속했을 때 Google 로그인이 실패했다

- 증상: EC2 공개 IP와 8082 포트로 CRM에 접속한 뒤 Google 로그인을 누르면 `400 invalid_request`가 발생했다.
- 확인: 오류 세부정보에서 Google에 전달된 `redirect_uri`가 `http://공개IP:8082/login/oauth2/code/google`인 것을 확인했다. IP 주소에 `https://`만 붙여도 Google Cloud 콘솔에서 등록이 거부됐다.
- 해결: DNS A 레코드를 EC2 탄력적 IP에 연결했다. Nginx가 외부 요청을 받아 Spring Boot의 8082 포트로 전달하도록 설정하고, Certbot으로 HTTPS 인증서와 HTTP → HTTPS 리디렉션을 적용했다.
- 검증: `https://www.crm.n-e.kr/login`에서 로그인 화면이 열리는 것을 확인했다.

## 2. EC2에 SSH로 접속하지 못했고 내부 앱 응답도 확인할 수 없었다

- 증상: 내 PC의 WSL에서 `127.0.0.1:8082/login`을 조회했을 때 `curl` 결과가 `000`으로 나왔다. EC2에 SSH로 접속하는 과정에서도 오류가 발생했다.
- 확인: WSL에서 실행한 `127.0.0.1` 요청은 내 PC 내부로 향했다. SSH는 처음에 키 파일명이 달랐고, 이후에는 WSL에서 키 권한이 `0444`로 표시되어 OpenSSH가 키를 사용하지 않았다.
- 해결: 실제 키 파일을 WSL의 `~/.ssh`로 복사하고 권한을 `600`으로 설정했다. SSH에 접속한 뒤 EC2 터미널에서 동일한 내부 주소를 다시 조회했다.
- 검증: EC2 SSH 접속에 성공했고, EC2 내부의 `/login`에서 `HTTP 200`을 확인했다.

## 3. HTTPS 적용 후에도 Google OAuth 콜백 주소가 일치하지 않았다

- 증상: 브라우저에서 HTTPS로 접속했는데 Google 로그인 시 `400 redirect_uri_mismatch`가 발생했다.
- 확인: Google Cloud 콘솔에 등록한 콜백은 `https://`로 시작했지만, 오류 화면에 표시된 실제 `redirect_uri`는 `http://`로 시작했다. Nginx가 HTTPS 연결을 처리한 뒤 Spring Boot에 내부 HTTP로 요청을 전달하는 구조였다.
- 해결: Nginx에서 `X-Forwarded-Proto`를 전달하도록 설정하고, EC2의 `crm.env`에 `SERVER_FORWARD_HEADERS_STRATEGY=native`를 적용했다. Google Cloud 콘솔의 운영 콜백을 `https://www.crm.n-e.kr/login/oauth2/code/google`로 등록했다.
- 검증: 최종 재배포 후 Google 로그인을 진행해 CRM의 매장 운영 현황 화면으로 돌아오는 것을 확인했다.

## 4. CRM 서비스를 재시작하자 `502 Bad Gateway`가 발생했다

- 증상: `crm` 서비스 재시작 후 공개 주소에서 502가 발생했고, EC2 내부 `/login`도 HTTP 응답을 받지 못했다.
- 확인: `journalctl -u crm`에서 `Schema-validation: missing table [image]`를 발견했다. 운영 MySQL에서 `image` 테이블은 이미 삭제됐지만, 기존 배포 JAR에는 `Image` 엔티티가 남아 있었다. `prod`의 `ddl-auto=validate`가 이 불일치를 감지해 Spring Boot가 시작을 완료하지 못했다.
- 해결: 팀원이 PR #40에서 이미지 관련 코드를 제거한 것을 확인한 뒤, PR #41로 `develop`의 변경 사항을 `main`에 반영해 운영에 재배포했다.
- 검증: GitHub Actions의 CI #88과 CD #2가 성공했다. EC2 내부 `/login`에서 `HTTP 200`을 확인했고, 공개 HTTPS 주소에서 Google 로그인 후 매장 운영 현황과 로그아웃 버튼까지 확인했다.

## 오늘 배운 점

- `localhost`는 명령을 실행한 환경을 가리킨다. EC2 내부 포트를 확인할 때는 SSH로 접속한 터미널에서 실행 위치부터 확인해야 한다.
- OAuth 오류는 콘솔에 등록한 주소와 실제 요청에 담긴 `redirect_uri`를 비교하면 원인을 좁힐 수 있다.
- 502가 발생하면 EC2 내부에서 앱 포트에 먼저 요청해 본다. 응답이 없으면 `journalctl`로 앱 시작 로그를 확인한다.
- 운영 DB에서 테이블을 제거할 때는 해당 테이블을 참조하는 코드가 제거된 버전을 먼저 배포하고, 정상 응답을 확인한 뒤 DB 스키마를 정리한다.
