## 내 담당 역할

팀원이 개발한 기능이 정상적으로 빌드되고,
서버에서 실행되도록 관리한다.

| 구분 | 담당 내용 |
|---|---|
| GitHub | 협업 규칙, 권한, 브랜치 보호 |
| CI/CD | 빌드·테스트 및 배포 자동화 |
| AWS | EC2 서버, S3 파일 저장소 |
| DB | MySQL 배포 환경, 더미데이터, 백업 |
| 운영 | JAR 배포, 로그 확인, 재시작, 복구 |
| 문서 | 실행·배포 방법을 README에 기록 |

---

## 오늘 정리한 개념

### CI / CD

- **CI**: 코드 변경 시 빌드와 테스트를 자동 실행
- **CD**: 검증된 결과물의 배포 과정을 자동화
- 수동 배포를 먼저 성공시킨 뒤 CD로 연결하기

### JAR

- Spring Boot 앱을 실행할 수 있도록 묶은 파일
- 빌드한 JAR를 서버로 옮겨 실행하는 것이 기본 배포 흐름

### 환경변수 / 프로필

- 개발 환경과 배포 환경의 설정을 분리하는 방법
- DB 주소·비밀번호 등은 환경별로 주입
- 비밀번호와 API 키는 Git에 올리지 않기

### 권한의 종류

| 권한 | 관리 대상 |
|---|---|
| GitHub 권한 | 코드 수정, 리뷰, 병합, 저장소 설정 |
| AWS IAM 권한 | AWS 자원에 대한 접근 |
| 서비스 인가 | 사용자별 기능·매장 데이터 접근 |

## 기억할 점

- `prod`의 `ddl-auto=validate`는 테이블을 자동 생성하지 않는다.
  → 배포 전에 엔티티와 맞는 DB 테이블을 준비해야 한다.

- CI 성공이 모든 기능의 정상 동작을 뜻하지는 않는다.
  → 실제 테스트 코드와 배포 후 동작 확인이 필요하다.

- 배포 후에는 접속 여부뿐 아니라 다음도 확인한다.
  → 로그 확인 / 재시작 / 이전 버전 복구

- CI와 브랜치 보호 규칙의 실제 적용 여부는 내일 확인한다.
